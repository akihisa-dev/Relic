# Relic Version Management

## 依頼を判定する

1. `docs/development.md` のバージョン規則を確認する。通常の実装・修正・Issue対応・コミットだけなら番号を更新せず、次版計算も行わない。
2. バージョン更新の質問・相談は読み取りだけとする。実行依頼がある場合に以下へ進む。
3. Git状態と既存差分を確認し、未コミットの別作業を採番・コミットへ取り込まない。

## 次版を決める

1. 前回の更新コミットが反映した範囲と `app/package.json` のversionを確認する。従来の各コミットで更新済みの範囲も基点にできる。
2. 未反映コミットを古い順に読み、差分・目的・互換性から、後方互換性のない変更はMAJOR、互換性を保った機能追加・廃止予定の告知はMINOR、修正・文書・テスト・保守はPATCHとする。typeだけで決めない。
3. 反映済み変更と番号更新専用コミットを除外し、各コミットの区分を1件ずつ加算する。最大区分の1回にはまとめない。不明な反映範囲や区分だけ確認する。
4. `app/` で `pnpm version:next -- <現在値> <major|minor|patch>...` に区分を古い順に渡し、候補を確認する。コマンドはファイルを変更しない。
5. 互換性の変更は関連機能の移行・拒否・警告・テストで保護する。通常コミットに番号や採番区分を追加しない。

## 更新して検証する

1. `app/package.json` のversionを更新し、`app/` で `pnpm sbom:generate` と `pnpm licenses:check` を実行する。SBOMのapplication versionを同期する。
2. 必須検証、差分、番号の一致を確認し、`$relic-commit` で専用コミットを作る。件名は `chore: <更新後のversion> <日本語の説明>` とする。
3. 本文にscope、目的、内容、確認、影響、加算前の版、反映範囲の開始・終了コミットID、各コミットの区分を記録する。専用コミット自身は次回の加算対象にしない。
4. ステージ後の `pnpm version:check-staged`、コミット後の `pnpm version:check -- <base> <head>` を通す。自動検査は番号と形式の整合を確認し、区分・反映範囲の妥当性は実際の差分から確認する。
5. 更新実行の依頼には通常pushと反映確認を含む。ローカルのみの指定を優先し、`$relic-publish-github` の公開前検証を完了する。無関係な未公開コミット、曖昧な反映先は整理して確認し、force pushやタグ作成へ広げない。
6. push失敗時はコミットを保持し、未完了の公開確認と理由を報告する。完了時は採番根拠、反映範囲、検証、コミットID、push先と反映結果を示す。
