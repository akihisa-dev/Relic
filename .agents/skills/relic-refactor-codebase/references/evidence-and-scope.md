# 証拠と変更単位

## 目次

- 対象全体の調査と完成
- 証拠を集める順序
- 問題場面を記述する
- 調査候補を分類する
- 履歴から得た再利用可能な注意点
- 変更単位を決める

## 対象全体の調査と完成

大規模依頼は、調査・設計の対象を全体に保ち、実装を検証可能な単位へ分けて完成させる。変更行数、ファイル数、コミット数を達成目標にしない。

1. 正本の機能一覧と実装の入口・登録・依存経路を突き合わせ、対象の主要機能、共通処理、実行境界、状態所有、永続化、初期読込、配布を押さえる。全ファイルの精読は要求しないが、調べやすい箇所だけを全体の代表にしない。
2. 領域ごとに確認した入口・依存先と、問題あり・変更不要・未調査を短く保持する。候補の分類とは別に調査範囲を確認する。候補がないことだけで、その領域を調査済みにしない。記録は会話または一時成果物に置き、正本へ作業台帳を蓄積しない。
3. 主要問題を横断して、変更後の責務、状態の持ち主、依存方向を示す。共通原因を個別修正で隠していないか、移動だけで依存や二重状態が残らないかを判断する。設計と独立した単位は先行可能だが、後から全体設計との整合を確認する。
4. 各単位を全体設計へ対応付け、すべての利用側への切替、不要になった公開面・旧経路の撤去、必要な互換層の保持理由まで完了条件に含める。新しい部品を作っただけ、一つの利用側を移しただけでは再構成完了ではない。
5. 最終的に、調査対象一覧、変更前後の構造、利用側と旧経路の残存参照、境界をまたぐ検証結果を照合する。対象内の未調査や重要な未確定問題を対象外へ分類し直して終了しない。実施不能なら完了した部分と残る必須作業を報告する。
6. 局所問題しか見つからなくても、問題探索で終わらず下記の全体再設計を行う。現行維持しか成立しないと判断した場合は、検討した横断案と採用できない根拠を提示する。大規模実装の依頼は未達として扱い、変更なしや局所改善を代わりの完了にしない。

## 構造的な成果条件

大規模実装の成功には、以下をすべて満たす。個数や行数で形式的に大きくせず、実際に責務と利用関係が変わったことを確認する。

- **全体設計**: 主要領域と共通基盤について、責務の配置、依存方向、状態と処理の寿命を変更前後で示す。ファイル一覧だけでは設計としない。現行のディレクトリ構成は変更不可の契約ではない。
- **横断的な実装**: 全体依頼では、複数の主要領域と、それらが使う共通基盤の間で、実際の責務・依存・状態所有を変更する。指定領域では、その主要な処理経路全体を再構成する。未変更の領域は新構造との接続と維持理由を説明する。
- **移行の完結**: 共通部品を作るだけで終えず、関係する利用側を切り替え、重複した判断や状態、不要な旧API・旧経路を除く。必要な互換層は新しい所有者へ処理を委ね、独立した二重実装を残さない。
- **構造の改善**: 複数領域へ同じ変更を加える代表例を選び、変更箇所・判断の所有者・テスト境界がどう整理されたかコードで示す。性能を改善したと主張する場合は別途同条件で測定する。
- **統合された検証**: 各単位のテストに加え、新しい境界をまたぐ主要経路と失敗条件を検証し、公開契約・保存データ・操作の互換性、依存方向、残存参照、正本の一致を確認する。

設計では、機能を表す処理と画面・OS依存処理の分離、共通規則の所有者への集約、状態と非同期処理の寿命の統一、過剰な抽象化と重複経路の撤去を横断的に比較する。すべての方式の採用を強制せず、具体的な処理経路と保守負担に基づいて組み合わせる。

例: 共有索引の所有者を再設計する場合、索引を作る処理だけでなく、複数ビューの購読・無効化・切替を移行して旧解析と二重状態を除く。巨大な画面ファイルから関数を別ファイルへ移しただけでは、この成果条件を満たさない。

## 証拠を集める順序

1. 現行HEAD、作業ツリー、対象の正本、`app/package.json` を確定する。
2. 対象の入口から、公開型、IPC、状態、I/O、永続化、UI、テストを追い、build・配布へ影響する経路はそこまで影響地図に含める。
3. `rg`、import・export、handler登録、購読、動的import、CSS import、Forge設定から実際の接続を確認する。
4. 変更理由や再発原因が不明な場合は、対象パスの `git log --follow`、変更理由が分かるコミット、後続のfix・perf・revertを確認する。
5. Issueが指定された場合はGitHub連携の一次情報を使う。取得できないIssueを推測で補わない。
6. 現行の対象テスト、測定script、baseline、workflowが何を検知し、何を検知しないか読む。

## 問題場面を記述する

候補を実装へ進める判断に次の項目を使う。関係しない項目は省き、未確定候補が独立した単位の着手を妨げないようにする。

| 項目 | 内容 |
|------|------|
| 変更・実行場面 | 例: 同じ設定ファイルへwriteとupdateが重なる |
| 観測される問題 | 例: 後から完了した処理が一方の変更を失わせる |
| コード経路 | 入口、所有状態、I/O、完了通知まで |
| 根拠 | 再現、テスト、測定、履歴、現行コード |
| 守る契約 | 保存形式、IPC、操作、表示、配布など |
| 修正後の所有者 | 状態や責務を一つだけ挙げる |
| 検証 | 正常、競合、失敗、取消、復旧、終了など |

「長い」「複雑」「重複して見える」は調査の入口であり、問題場面の代わりにしない。

## 調査候補を分類する

責務、状態所有、重複、名前と処理経路、依存方向、testability、非同期とerror、I/O・再計算・再描画、旧経路を調査面として列挙し、各候補を次のいずれかへ分類する。一時的な作業記録は会話中のplanや最終報告で保持し、現在仕様でない監査表を正本文書へ残さない。

| 状態 | 判定 |
|------|------|
| `confirmed` | 問題場面、コード経路、影響、修正後の所有者、検証を説明できる |
| `not-found` | 現行HEADでは問題を確認できず、変更しない |
| `insufficient-evidence` | 根拠が足りず、追加調査または保留が必要 |
| `out-of-scope` | 実在する可能性はあるが、今回の契約と独立している |

分類数を成果にせず、根拠のない `confirmed` や変更を正当化するための候補追加を行わない。全候補の分類が終わっていない場合は、包括調査を完了扱いにしない。

## 履歴から得た再利用可能な注意点

コミット `46a98f76b9f2905d4ff89b72618c094ffa2ab504` は、IPC、設定、共有索引、renderer、bundle、配布、検証、文書を同じ互換条件の下で改善した実例である。手順を固定化せず、次の原則だけを現行HEADへ再照合して使う。

- 境界の分割はファイル移動では完了しない。公開契約、互換アダプタ、利用側client、契約検査が一致して初めて境界になる。
- cacheや共有索引はhit率だけでは評価できない。生成、無効化、変更ファイルだけの更新、外部変更、切替、失敗後の復旧を一組で扱う。
- 状態保存の共通化は全操作を同じ直列化規則へ含める。後続の `f955b3e9` はwriteとupdateの競合が残り得たことを示すため、APIごとの正常系だけで完了しない。
- 不要描画の削減は停止条件だけでなく再開条件を列挙する。後続の `69c06623` は、入力、data、theme、size、simulation更新から一度だけ再開する検証が必要だと示す。
- 長寿命の監視処理は開始成功だけでは足りない。後続の `a6f4a573` は、実行中失敗、backoff、復旧時の再確認、workspace切替、終了時破棄、利用者通知までが境界であることを示す。
- 配布検査が通っても、実際のtoolchain・OS経路は別に壊れ得る。直後の `f5a683dd` は、対象環境のbuildを要する変更を静的なASAR検査だけで完了できないことを示す。
- 追加した回帰検査自体も現行HEADで継続確認する。baselineやSBOMの既存不一致を今回の回帰と混同せず、検査を弱めずに扱う。

これらのコミットは現在仕様の正本ではない。現行の正本文書、コード、tests、`app/package.json` と矛盾する場合は現行HEADを優先する。

## 変更単位を決める

同じ単位に含める目安:

- 同じ互換契約を変更または保護する
- 一方だけでは途中状態が検証不能になる
- 同じ状態所有や無効化規則を共有する
- 実装、回帰テスト、正本文書が一つの完了条件を作る

分離する目安:

- 利用者に見える結果や互換性が独立している
- 別の責務所有者と検証方法を持つ
- 片方を保留しても他方が完全に成立する
- 新たに見つかった問題で、当初の根拠と完了条件を広げる

変更単位ごとに、目的、非目的、問題場面、修正後の所有者、守る契約、対象path、依存する単位、検証、削除条件を記録する。着手する単位の根拠と検証方法を確認し、未確定の単位だけ追加調査へ戻す。旧経路がなければ削除条件は不要とする。
