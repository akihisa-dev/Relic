# Relic Codebase Refactoring

## 作業契約を固定する

1. 開始時のHEAD、`git status --short`、対象範囲を確認し、他者変更を保護する。
2. 機能追加ではなく現行の品質改善を扱う。行数や変更量でなく、複数の責務や境界を横断する再構成を対象とする。局所的な責務整理や一つの既知問題に閉じる場合は `$relic-audit-code-health` または対象領域のSkillへ渡す。調査・計画・レビューだけの依頼では編集しない。
3. 変更に関係するMarkdown、frontmatter、設定schema、保存済みデータ、ワークスペース境界、IPC、公開型、操作・表示、CSS読込順、配布資源を互換契約として押さえる。無関係な面まで記録を強制せず、旧形式や移行の要否は現行の正本と利用経路で確認する。
4. 実ユーザーデータや既存のRelicウインドウを検証に使わない。ユーザーが実画面確認を明示的に指示した場合だけ `$relic-test-development-app` に従い、その作業で起動した開発版と一時データを使う。
5. push、Release、外部公開は別途明示された範囲だけ対応Skillへ渡す。書き込み前は `$relic-guard-task`、コミット時は `$relic-manage-version` と `$relic-commit` を使う。未確認の互換処理、移行、旧形式を推測で削除しない。

## 現行HEADから影響地図を作る

1. `AGENTS.md`、`docs/INDEX.md`、`docs/development.md`、対象機能と設計の正本の必要な節、`app/package.json`、対象コードを読む。コマンドや構成を履歴から推測しない。
2. 対象の入口と呼出元、公開API・型、main・preload・rendererとIPC、状態所有、I/O・永続化、UI接続、テストを追跡し、build・配布へ影響する経路はそこまで確認する。全体依頼では主要な入口と責務を広く確認して実害と波及範囲から深掘り先を選び、指定領域では無関係な整理へ広げない。
3. import・export、登録・購読、cacheの生成・無効化、保存・終了待ちを双方向に追う。
4. 互換処理の理由や再発原因が不明な場合は、対象のGit履歴、関連Issue、後続修正、revertを確認する。単発事例は恒久規則にせず、全判断を現行実装へ再照合する。
5. 候補の根拠や変更単位の判断に迷う場合は [証拠と変更単位](references/evidence-and-scope.md) を読む。
6. 調査した候補を `confirmed`、`not-found`、`insufficient-evidence`、`out-of-scope` に分類する。未分類の候補を残したまま「包括的に調査済み」と報告しない。

## 実在する問題を確定する

1. 「どの変更時または実行時に、誰に何が起きるか」を再現またはコード経路で説明する。保守上の問題も対象とし、同じ変更で複数箇所の修正が必要、異なる変更理由の密結合、依存のため単独検証できない、といった具体的な負担を示す。利用者向け不具合の再現を必須にせず、行数、関数数、依存数、診断点、coverageだけで問題を確定しない。
2. 状態・責務の散在、環境依存処理の混在、境界の曖昧さ、非同期競合、重複I/O・再計算・描画、無効化漏れ、不要な初期読込・旧経路、回帰検知不足を候補とする。該当しない項目は実装しない。
3. 候補ごとに根拠、問題場面、現所有者、影響、守る互換性、修正後の所有者、検証方法を記録する。根拠不足は保留にする。
4. 分割を前提にせず、統合、依存方向の修正、状態所有の集約、抽象化の除去も比較し、最小の構造変更を選ぶ。
5. 巨大なmanager、service、hook、context、store、共通モジュールへ問題を移すだけの案を拒否する。新抽象化の利用者、公開面、変更理由、状態寿命を説明できる場合だけ導入する。

## 変更単位と順序を設計する

1. 問題を、目的、守る契約、変更範囲、完了条件、依存する変更が明確な単位へ整理する。独立課題は分離し、同じ不変条件を共有する密接な変更は機械的に分断しない。
2. 純粋処理、実行環境依存処理、状態所有、公開境界を区別し、依存方向を明示する。UIからOS処理を直接参照させず、互換アダプタから現行modelへ旧形式を漏らさない。
3. 依存関係に合わせて順序を選び、各段階で検証可能にする。次は一例であり固定順ではない。
   1. 既存テストが守る動作を確認し、不足する重要な契約だけテストまたは測定で固定する。現在の不具合を正しい仕様として固定しない。テスト追加・修正・失敗時は `$relic-test-code` を使う。
   2. 公開契約と互換層を維持したまま、新しい責務境界を作る。
   3. 純粋処理、状態所有、I/Oの順に移し、呼出側を段階的に切り替える。
   4. 非同期の取消・失敗・再試行・終了・切替条件を固定する。
   5. 全参照と互換性を確認してから旧経路、未使用CSS、assetを削除する。
4. 性能変更では、cache hitだけでなく無効化、外部変更、保存待ち、ワークスペース切替、失敗後の復旧を同じ設計で扱う。
5. 変更途中で新しい独立問題を見つけても無制限に取り込まず、根拠と影響を残して別課題候補にする。
6. 着手する単位の問題、修正後の所有者と依存方向、守る契約、検証、旧経路があれば削除条件を短く定める。全候補の調査完了や定型表の全欄を着手条件にせず、未確定部分と独立した単位から進める。
7. 通常作業は `AGENTS.md` の分担規則に従い、調査から検証まで完結する単位で委譲する。管理役は共有境界と依存順序を決め、担当範囲、他者変更の保持、受入条件を伝える。同じ状態や公開契約に依存する編集は順序を付ける。

## 変更に対応する回帰検知を作る

1. 変更が影響する契約と失敗経路を選ぶ。
2. 件数やcoverage増加を目的にしない。型、安全条件、構造規則、初期読込境界を弱めず、coverage割合を合否条件にしない。
3. `app/package.json` と `docs/development.md` でコマンドの存在と意味を再確認し、対象テストと型検査を基本に、変更の影響と専門Skillの必須条件に応じて全体検証を選ぶ。
4. 構造変更では通常テストに加えてプロセス境界と循環依存を、性能変更では同一fixture・warmup・実行回数の中央値とI/O回数を、初期読込変更ではproduction manifestの静的import経路を確認する。
5. 配布変更ではASAR allowlist、必須entry、resources、OS差、ライセンス、第三者通知、SBOMを確認する。配布buildが必要な変更では `$relic-debug-packaging` を併用する。
6. 変更に応じた検証を選ぶ際は [互換性と検証](references/compatibility-and-verification.md) を読む。全項目を毎回実行せず、必須確認が通れば新しい変更・失敗・未解決の懸念がない限り検証を広げたり繰り返したりしない。

## 正本と実装を同期する

1. 責務、依存方向、データモデル、IPC、保存形式、性能条件、配布内容、検証方法が変わった場合だけ、対応する正本文書を同じ変更で更新する。
2. 作業履歴や一時測定値を正本へ蓄積せず、現在成立する設計と運用だけを書く。
3. 文書の追加・移動・削除があれば `$relic-maintain-docs` に従い、索引を同期する。

## 完成を監査する

1. 各単位の差分と検証証拠に加え、単位間の状態所有、公開契約、残存参照を照合する。担当者の成功報告だけで完了とせず、同じ検証を理由なく再実行しない。必要な検証を完了し、`git diff --check`、全差分、生成物、残存参照を確認する。
2. 調査候補の分類と保留理由、問題場面の解消、責務と境界、互換性、変更した性能・配布への効果、回帰検知、正本との一致を根拠付きで評価する。巨大な抽象化、循環依存、二重状態、互換分岐の拡散へ置き換わっていないか確認する。
3. 既存失敗と今回の回帰を基準実行と差分で分ける。比較元を確認できなければ既存失敗と断定せず、共有作業ツリーの巻き戻しを基準測定に使わない。未確認OS、未測定性能、取得できないIssueなどを成功と表現しない。
4. 改善結果、主要根拠、互換性、検証、正本、未確認事項を報告する。実装依頼では検証・既定コミットまで進め、必須の未完了を保留扱いで完了にしない。問題が確認できなければ変更なしで終了してよい。調査・計画だけなら編集せず、根拠、推奨する変更単位と順序、検証方法を報告する。

## 隣接Skillへ接続する

- 局所的な診断や候補整理、React警告、単一の巨大ファイル・初期読込・性能調査は `$relic-audit-code-health` を優先する。包括的な再構成の調査・計画は本Skillで扱える。
- 実装中のIPC、設定、ファイル、検索、エディタ、出力、UI、可視化は対応するrelic-change系Skillを併用し、その領域固有の安全条件を受け持たせる。
- テスト失敗だけ、テスト追加だけは `$relic-test-code`、依存更新は `$relic-update-dependencies`、配布障害は `$relic-debug-packaging` を優先する。
- 発火例、対象外、隣接Skillとの境界を変更するときは [ルーティング評価](references/routing-evaluation.md) でdescriptionを再評価する。
